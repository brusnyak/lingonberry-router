One local router for every AI agent on your machine.

Your agents hand work to Lingonberry. It picks a worker, runs the task, checks the result, and writes a receipt you can read. Nothing leaves your machine except the calls to the workers you configured.

How a request moves

Every run has a receipt. You can see the class, skill, hook, gate and the steps taken, and the output is stored with it.

1. Route

The prompt is classified by whole words (for example "review" and "preview" are different), a skill is matched by its name and description, and its body is added to the prompt. Long prompts are split at paragraph breaks and merged afterwards.

2. Dispatch

The router picks a worker from the ones that are available: its CLI agent with its own login, or a provider key. Workers are tried in order, with failover and cooldown when one fails.

3. Gate and record

The gate for the task class runs on the output. The session keeps the prompt, the router decision, every step and the output, and a receipt id you can look up later with GET /receipts/:id.

Keys and security

The router reads your keys from your environment, your env files, and the credential files of the agents you already use. It records names only. A value is read at the moment of a call and not stored.

Your keys stay yours

API keys are used only by the owner: the menu bar app and the local CLI. An agent that calls the router without the app's origin gets its own CLI worker and never your keys. Checked with curl on a running daemon.

Local only

The HTTP API listens on 127.0.0.1 and refuses any Host header that is not loopback, so a web page cannot use it through DNS rebinding. Browser pages can read the snapshot only from the app's own origin.

No shell from HTTP

Jobs created over HTTP cannot carry a shell command. Shell jobs exist only in the router's own configuration. Rejected requests return 403 and are covered by tests.

Install

There is no release binary yet. Build from source with the Rust toolchain. The menu bar app is a Tauri bundle built from the same source.

# build the core and the menu bar app (macOS)
cd core && cargo build --release
cd .. && npm install && npm run build:web
sh tray/scripts/prepare-core.sh
cd tray && ../node_modules/.bin/tauri build --bundles app

# check your machine: which agents and keys were found, nothing is run
lingonberry-core discover
lingonberry-core doctor

# see the routing decision for a prompt, nothing is run
lingonberry-core route "review the auth middleware" --caller claude

# register the router with your agents (preview first, then apply)
lingonberry-core self-config
lingonberry-core self-config --apply

Registration writes one skill, one constitution pointer, one MCP entry and a marked two-line block in each agent's instruction file. Each file is backed up before it is changed, and the block can be removed by deleting the lines between the markers.

Menu bar

The app sits in the menu bar and shows the router only. It stays idle until something is running.

Graph

With nothing running: one router node. While work runs: the calling agents, the router, and the workers in use, joined by lines.

Workers and providers

Every key the router found, grouped by provider, with its calls in the last 24 hours and its calls-per-minute limit. You can change a limit with the buttons.

Sessions

Each session shows the prompt, the router's decision (class, skill, command, hook, gate, attempts), the worker's output, and the steps. The output can be copied.

API

Local HTTP on 127.0.0.1:8799. Read endpoints are open to local callers. Endpoints that change state accept only the app's origin. Agent runs accept calls with no Origin header, and those calls never receive your keys.

EndpointWhat it doesWho
GET /snapshotWorkers, providers, sessions, jobs, system figureslocal
POST /api/routeRouting receipt for a prompt. Runs nothing.local
POST /api/runDispatch one task. Keys only for the app.local
POST /api/fanoutSeveral prompts in parallellocal
GET /receipts/:idOne receipt by idlocal
POST /kill/:pidStop a running workerapp only
POST /api/jobsCreate a router job (prompt only)app only

From an agent, the caller name is passed with --caller or the ROUTER_CALLER environment variable. It is written into every receipt.
